## 0. 阅读指南

### 0.1 需求编号规则

| 前缀 | 含义 |
|---|---|
| `G-REQ-*` | 全局 / 跨模块约束 |
| `A-REQ-*` | 模块 A（图形叠加） |
| `B-REQ-*` | 模块 B（vMix 回放 / OBS 转场） |
| `C-REQ-*` | 模块 C（提示 / 编排 / 监看） |
| `S-REQ-*` | 共享壳层 |
| `*-NFR-*` | 非功能需求 |
| `AC-*` | 验收标准 |
| `R*` / `RC*` | 待现场验证项 |

### 0.2 术语表

| 术语 | 含义 |
|---|---|
| **CLEAN** | OBS 中唯一送往 vMix 的场景，不含浮窗、不含回放画面 |
| **LIVE** | OBS 直播场景 = CLEAN + 浮窗 |
| **REPLAY** | OBS 回放场景 = vMix 回传 NDI + REPLAY 标识 + 浮窗 |
| **回路延迟 L** | OBS→NDI→vMix→回放处理→NDI→OBS 的往返延迟，约 130–300ms |
| **监看延迟 D** | 导播页看到的画面相对真实播出的滞后，200–3000ms |
| **打点** | 在 vMix 回放中创建事件（Mark In/Out） |
| **裁切（Clip）** | 定义片段的入点与出点，不涉及上屏 |
| **回溯量 XX** | 裁切入点相对"所见时刻"往回的秒数（lookback） |
| **上屏** | 回放画面成为 OBS 当前节目输出 |
| **cut point** | stinger 转场中遮罩盖满、场景完成切换的那一瞬 |
| **提示（Cue）** | 投递给某受众的通知，带优先级、生命周期、可选确认 |
| **受众（Audience）** | 提示接收频道：`director` / `cast` / `floor` |
| **提前量（Lead）** | 距目标时刻的秒数，如 T-15s |
| **渐进升级** | 同一倒计时在多个时间点以递增优先级重复提示 |
| **回执（Ack）** | 接收端确认已看到提示 |
| **WHIP** | WebRTC HTTP **Ingest** Protocol —— **推流（发布）** |
| **WHEP** | WebRTC HTTP **Egress** Protocol —— **拉流（播放）** |
| **叠加（Overlay）** | 渲染在视频画面之上的图形层 |
| **模板（Template）** | 可复用的图形结构，含固定排版 + 可变槽位 |
| **实体（Entity）** | 数据记录：选手 / 解说 / 队伍 / 赞助商 |

### 0.3 全局硬约束速览

| # | 约束 | 出处 |
|---|---|---|
| 1 | vMix 回放功能需 **4K / Pro / Max** 版本 | 官方 |
| 2 | OBS 画布 / NDI 输出 / vMix 回放会话**三者格式必须完全一致**（含 59.94 vs 60） | ✅ 官方 |
| 3 | 送 vMix 的 NDI 必须用 **NDI Dedicated Output 滤镜**，禁用主输出 | G-REQ-103 |
| 4 | 浮窗**不得**放进 CLEAN 场景 | G-REQ-104 |
| 5 | vMix HTTP API **无鉴权** | ✅ 官方 |
| 6 | 制作机**不得安装 VPN / Tailscale** | ✅ DistroAV 官方警告 |
| 7 | LIVE 场景**禁止**使用 vMix 回传画面（音画同步） | B-NFR-08 |

## 1. 项目概述

### 1.1 背景

街机音游（中二节奏）赛事直播。原始方案为「OBS 做节目总切换 + vMix 做纯视频回放机」，但实操中暴露出三个层面的缺口：

1. **画面层** —— 需要叠加选手名、导播/解说名、感谢列表等自定义图形，且要求可热改、可换图
2. **操作层** —— vMix 回放面板无法远程完整控制；转场需要跨软件联动
3. **人与时间层** —— 解说不知道何时轮到自己、导播不知道操作是否被接收、缺少独立监看手段

### 1.2 系统总览

```
┌──────────────────── 共享壳层 (Shell) ────────────────────────┐
│  连接池 · 共享状态源 · 配置服务 · 日志服务 · WS 广播中枢        │
│  同一 Web 应用，多页面路由                                     │
└──┬────────────────────┬────────────────────┬────────────────┘
   │                    │                    │
┌──▼─────────┐   ┌──────▼───────┐   ┌────────▼─────────┐
│  模块 A    │   │   模块 B     │   │    模块 C        │
│ 图形叠加   │◄──┤ vMix 回放    ├──►│ 提示/编排/监看   │
│            │   │ OBS 转场     │   │                  │
│ · 选手名称 │   │ · 裁切控制   │   │ · 分级提示       │
│ · 解说名牌 │   │ · 播放控制   │   │ · 倒计时编排     │
│ · 感谢列表 │   │ · 完整面板   │   │ · 导播监看       │
│ · 媒体库   │   │ · 转场面板   │   │ · 转场大提醒     │
└────────────┘   └──────────────┘   └──────────────────┘
```

### 1.3 目标

1. **模块 A**：浏览器源图形叠加，支持选手名 / 解说名 / 感谢列表，可自定义图片与模板
2. **模块 B**：网页中**完整**实现 vMix 回放控制面板（13 个功能区）；通过 WebSocket 控制 OBS 转场与场景切换
3. **模块 C**：向导播 / 解说 / 现场投递分级提示（含倒计时与回执）；独立导播页可拉流监看；转场时悬浮大提醒
4. 三模块**完全解耦**：任一模块崩溃不影响其余模块
5. 支持单机部署与双机部署（OBS 与 vMix 异机双 IP）

### 1.4 非目标

- ❌ vMix 多机位回放（仅回放 OBS 最终节目输出这一路；机位函数保留封装但不做 UI）
- ❌ vMix 音频处理 / 回放音频（vMix 完全不参与音频）
- ❌ VOD 导出、精彩集锦编排自动化
- ❌ 取代对讲机 / IFB（模块 C 是辅助提示，不是通讯替代）
- ❌ 复杂运动图形（专业图形系统领域）
- ❌ 观众可见的任何交互

## 2. 全局架构

### 2.1 部署拓扑

**模式 1：单机**

```
中转服务 :3000(overlay) :3001(control)
   → OBS ws://127.0.0.1:4455
   → vMix http://127.0.0.1:8088
   → MediaMTX :8889（可选，同机）
```

**模式 2：双机（推荐）**

```
OBS 机 (192.168.10.11)              vMix 机 (192.168.10.12)
  中转服务 + 控制台                   vMix Pro
  OBS ws://127.0.0.1:4455      ──►  http://192.168.10.12:8088
  NDI Dedicated Output         ──►  NDI Output 2
  MediaMTX :8889（可选）
```

| ID | 需求 |
|---|---|
| G-REQ-101 | vMix 与 OBS 的地址必须**完全配置化**，不得硬编码。默认 `127.0.0.1` |
| G-REQ-102 | 切换单机/双机部署，**只允许修改配置文件**，不得改动代码 |

### 2.2 信号流

```
【视频】
游戏采集 ──┐
选手摄像头 ─┤→ [CLEAN 场景] ─NDI Dedicated Output─→ vMix ─→ [Replay 输入]
计分条    ─┘        │                                   │
                    │                                   ├─→ Output 2 (Source=Replay)
                    │                                   │        │ NDI
                    │                                   │        ▼
                    │                                   │  [vMix 回放源] ──┐
                    └───────────────┐                   │                   │
                                    ▼                   │                   ▼
                            [LIVE 场景]            [REPLAY 场景] ◄───────────┘
                              + 浮窗                  + REPLAY 标识
                                    │                  + 浮窗(共享实例)
                                    └────────┬─────────┘
                                             ▼
                                        直播 / 录制

【监看（可选）】
OBS ──WHIP 推流──► MediaMTX ──WHEP 拉流──► 导播页浏览器
     :8889/live/whip          :8889/live/whep

【控制】
所有控制台 ──WebSocket──► 中转服务 ──┬──► OBS WebSocket
                                     └──► vMix HTTP API
```

> **G-REQ-103**：送 vMix 的 NDI **必须**由 OBS 的 `NDI Dedicated Output` 滤镜挂载在 CLEAN 场景上，**禁止**使用 `工具 → NDI 输出设置` 的主输出。理由：REPLAY 场景含 vMix 回传源，用主输出会形成无限镜像。
>
> **G-REQ-104**：浮窗源不得放入 CLEAN 场景，须作为共享源实例同时出现在 LIVE 与 REPLAY 场景中，以保证切换时动画状态不中断、回放画面不被烧录浮窗。
>
> **G-REQ-105**：OBS 画布 / NDI 输出 / vMix 回放会话三者分辨率、帧率、逐行必须**完全一致** ✅（官方硬约束：*"NDI sources can also be used with Instant Replay as long as they are in the same format as the current Replay Session"*）。

### 2.3 延迟模型 ★

本系统存在**三个独立的延迟**，必须严格区分，**不可相互替代**。

| 延迟 | 符号 | 量级 | 影响域 | 补偿方式 |
|---|---|---|---|---|
| **回路延迟** | L | 130–300ms | 模块 B 打点 | `markDelayMs`（B-REQ-502） |
| **监看延迟** | D | 200–3000ms | 模块 C 视线 | 以真实播出时刻为计时基准（C-REQ-407） |
| **转场遮罩窗口** | W | 200–600ms | 模块 B 上屏 | stinger Transition Point（B-REQ-1101） |

**回路延迟 L 构成**（粗算）：

```
OBS 渲染              1–2 帧
OBS → NDI 编码        ~1 帧
网络传输              <1 帧
vMix NDI 输入缓冲      1–3 帧   ← 可调，LAN 上设最低
vMix 回放处理 + 输出   ~2 帧
vMix → NDI 回传       1–2 帧
OBS NDI 源缓冲        1–2 帧   ← 可调，设最低
──────────────────────────────
合计                   130–300ms
```

**监看延迟 D 对比**：

| 方案 | D 量级 |
|---|---|
| WHEP | 200–500ms |
| `GetSourceScreenshot` 轮询（3fps） | 1–3s |
| HLS | 3–10s |

| ID | 需求 |
|---|---|
| G-REQ-106 | 文档与 UI 须明确区分 L / D / W 三个延迟，任何补偿逻辑不得混用 |
| G-REQ-107 | 所有倒计时以**真实播出时刻**为基准（服务端单调时钟），禁止以「客户端显示的当前画面」为基准 |
| G-REQ-108 | 两端 NDI 缓冲须调至最低 |

### 2.5 冻结接口（跨模块契约）

```ts
// ══════ 模块 A 对外 ══════
interface PlayerContextProvider {
  getCurrent(): PlayerEntity | null;
}

interface OverlayModeController {
  push(mode: 'live' | 'replay', payload?: { label?: string; speed?: number }): void;
}

// ══════ 模块 B 对外 ══════
interface ReplayCapability {
  // ① 只读预检，无副作用
  preflight(): Promise<{ ok: boolean; blockers: string[]; warn: string[] }>;
  // ② 登记 / 撤销待执行意图（参与意图对账）
  arm(intent: ReplayIntent): Promise<void>;
  disarm(): Promise<void>;
  // ③ 立即执行
  execute(intent: ReplayIntent): Promise<void>;
}

type ReplayIntent = 'clipAndAir' | 'clipOnly' | 'air' | 'backToLive';

type ReplayEvent =
  | { t:'phase';        phase: ReplayPhase; at: number }
  | { t:'clip:ready';   durationMs: number; lookbackMs: number }
  | { t:'air:start';    player: PlayerSnapshot | null; at: number }
  | { t:'progress';     positionMs: number; durationMs: number; remainingMs: number }
  | { t:'air:ending';   remainingMs: number }
  | { t:'air:ended';    at: number }
  | { t:'air:returned'; at: number }
  | { t:'error';        code: string; msg: string };

// ══════ 模块 C 对外 ══════
interface CuePublisher {
  publish(cue: CueInput): Promise<{ cueId: string }>;
  scheduleCountdown(opts: CountdownInput): Promise<{ cueId: string; ok: boolean; blockers: string[] }>;
  cancel(cueId: string): void;
}
```

| ID | 需求 |
|---|---|
| G-REQ-109 | 模块 B **不得**修改 `currentPlayer`；模块 C **不得**修改 `currentPlayer`；模块 C **不得**直接调用 OBS 写接口 |
| G-REQ-110 | 模块 A **不依赖 obs-websocket**（见 A-REQ-001） |
| G-REQ-111 | 模块 B 的事件发射必须 fire-and-forget：订阅者抛异常不得中断 B 主流程（B-REQ-5107） |
| G-REQ-112 | 任一模块崩溃或停止，**不得**影响其余模块功能（C-REQ-1002） |

### 3.4 OBS 场景结构（必须严格遵循）

```
【源面板】

  ├─ 源「游戏采集」              (窗口/采集卡)
  ├─ 源「选手摄像头」
  ├─ 源「浮窗-主」               ← 浏览器源 /render/main（全局共享实例）
  ├─ 源「vMix 回放」             ← NDI Source，指向 vMix Output 2
  ├─ 源「REPLAY 标识」           ← 图片/文本源
  └─ 源「浮窗-致谢」             ← 浏览器源 /render/credits（仅致谢用）

【场景】

  ┌─ 场景「CLEAN」  ← 唯一送往 vMix 的场景
  │    ├─ 游戏采集
  │    ├─ 选手摄像头
  │    └─ 【滤镜】NDI Dedicated Output   ★ 挂在这里，不是 Tools 菜单
  │
  ├─ 场景「LIVE」
  │    ├─ 【场景源】CLEAN
  │    └─ 浮窗-主
  │
  └─ 场景「REPLAY」
       ├─ vMix 回放
       ├─ 浮窗-主            ← 与 LIVE 共用同一个源实例
       └─ REPLAY 标识
```

**vMix 侧配置**：

| 项 | 设置 |
|---|---|
| 回放会话格式 | 与 OBS 画布**完全一致** |
| Output 2 | Source = 回放输入；开启 NDI |
| NDI 输入音频 | **关闭**（video-only 原则） |
| 回放输出转场 | **Cut**（转场交给 OBS） |
| 缓冲长度 | 记录实测值，用于 `clip.maxLookbackMs` |

**OBS 浏览器源设置**（浮窗）✅ 核验自 obs-browser 源码：

```
宽度 × 高度：1920 × 1080
自定义帧率：60（或与画布一致）
shutdown = false              ★ 必须
restart_when_active = false   ★ 必须
```

| ID | 需求 |
|---|---|
| G-REQ-204 | 浏览器源必须始终开启，`shutdown = false`、`restart_when_active = false`。否则源隐藏时 CEF 进程退出，再显示时重连丢状态 |

## 4. 模块 A：浏览器图形叠加

### 4.1 目标与非目标

**目标**

1. 渲染端**只画不管**：内容全部由外部指令驱动，页面永不刷新
2. 模板可扩展：新增一种图形 = 新增一个模板 + 一处注册
3. 媒体库可上传：运营人员无需碰代码即可换图
4. 支持三大图形类型：**选手名称** / **导播·解说名称** / **感谢列表**

**非目标**

- ❌ 复杂运动图形（用 vMix GT / CasparCG）
- ❌ 视频播放类模板（用 OBS 媒体源）
- ❌ 观众端可见的交互

### 4.2 架构

│  ├ 模板注册表（内置 + 自定义）                            │

| ID | 需求 |
|---|---|
| A-REQ-001 | **模块 A 不依赖 obs-websocket**。显隐完全由渲染端页面内部 DOM 状态决定，**不通过** `SetSceneItemEnabled` 控制。理由：① 避免 OBS 硬切导致动画中断；② 避免引入 OBS 依赖；③ 消除"切场景时浮窗闪一下" |

### 5.1 目标

### 5.2 状态机

```
                    ┌──────────────────────────────┐
                    │                              │
   ┌──────┐  startRecording   ┌────────┐  stopRecording  │
   │ IDLE │──────────────────►│ ARMED  │─────────────────┘
   └──────┘◄──────────────────┴───┬────┘
                                  │ clip() 或 clipAndAir()
                                  ▼
                            ┌──────────┐
                            │ MARKING  │  (markDelayMs + 裁切序列)
                            └────┬─────┘
                                 │ 片段已选中
                                 ▼
                   ┌──────────────────────────┐
                   │          CUED            │
                   │ (已裁切未上屏)            │◄──┐
                   │  微调入出点 / 延长尾部     │───┘
                   └────┬──────────────┬──────┘
              air()     │              │ discard()
                        ▼              ▼
                   ┌──────────┐    (ARMED)
                   │   AIR    │
                   └────┬─────┘
                        │ backToLive()
                        ▼
                   ┌──────────┐
                   │RETURNING │
                   └────┬─────┘
                        │ 200ms 后
                        ▼
                     (ARMED)

   任意状态 ──异常──► FAULT ──reset()──► ARMED
```

| 状态 | 语义 | 允许操作 | 按钮呈现 |
|---|---|---|---|
| `IDLE` | 回放未录制 | 启动录制 | 全部禁用 |
| `ARMED` | 录制中，可触发 | 裁切、裁切并上屏、转场、改选手 | 主按钮可用 |
| `MARKING` | 裁切执行中（≤1s） | 无（锁定） | 转圈 |
| `CUED` | 片段已裁切并选中，未上屏 | 微调入出点、延长尾部、上屏、丢弃 | 上屏 + 丢弃 |
| `AIR` | 回放已上屏 | 暂停/播放/逐帧/微调/回直播 | 显示回程按钮 |
| `RETURNING` | 回程中（≤500ms） | 无（锁定） | 转圈 |
| `FAULT` | 异常 | 复位、查看日志 | 红色告警 |

| ID | 需求 |
|---|---|
| B-REQ-202 | `MARKING` / `RETURNING` 为**瞬态**，期间必须锁定宏触发（`busy` 锁），防止连点造成指令交叉 |
| B-REQ-203 | 瞬态最长存活时间 = 4s。超时未迁移 → 强制转 `FAULT` 并写日志 |

### 5.6 裁切（Clip）★

#### 5.6.1 三种裁切模式

| 模式 | 语义 | 主路径函数 | 适用 |
|---|---|---|---|
| **即时裁切** | 一步建立 `[所见时刻 − XX, 所见时刻]` 并选中 | `ReplayMarkInOut` | 主路径：刚发生的瞬间 |
| **开放出点** | 先建入点，出点随操作员后续锚定而延长 | `ReplayMarkInOut` → `ReplayUpdateSelectedOutPoint` | combo 未结束 |
| **固定长度** | `[所见时刻 − XX, 所见时刻 − XX + L]` | `ReplayMarkInOut` → 微调 | 集锦等需精确时长 |

#### 5.6.2 核心序列

**即时裁切**

```
1. 前置校验（phase === ARMED、连接健康、recording === true）
2. 状态 → MARKING
3. ReplaySelectChannel{A|B}          ★ 必须显式选通道，见 B-REQ-523
4. sleep(markDelayMs)                ← 对齐操作员所见时刻
5. ReplaySelectEvents{eventList}  { Channel }
6. ReplayMarkInOut  { Value: XX秒 }  ← 一步建立 [now−XX, now] 并选中
7. 状态 → CUED（持久）
```

**开放出点模式**（追加）

```
8.  操作员等待（时间不定，可能数十秒）
9.  ReplayUpdateSelectedOutPoint { Channel }   ← 出点 = 当前缓冲位置
10. 可重复步骤 9 继续延长
```

**帧级微调**（`CUED` / `AIR` 均可用）

```
ReplayMoveSelectedInPoint  { Value: ±帧数, Channel }
ReplayMoveSelectedOutPoint { Value: ±帧数, Channel }
```

**入/出点核对**

```
ReplayJumpToSelectedInPoint  { Channel }
ReplayJumpToSelectedOutPoint { Channel }
ReplayJumpToNow              { Channel }   ← 核对完必须回位
```

**丢弃**

```
ReplayMarkCancel   ← 注意：无 Channel 参数，作用于当前选中通道
```

### 5.7 一键回放宏

**触发序列**（严格按序）：

```
 1. 前置校验（见 B-REQ-501）
 2. 状态 → MARKING，取 PlayerSnapshot，锁定 UI
 3. sleep(markDelayMs)                          ← 补偿回路延迟 L
 4. ReplaySelectChannel{A|B}
 5. ReplaySelectEvents{eventList}  { Channel }
 6. ReplayMarkInOut                { Value: XX秒 }
 7. ReplaySetLastEventText         { Value: snapshot.playerName }
 8. ReplaySetSpeed                 { Value: speed, Channel }
 9. ReplayPlayLastEventToOutput    { Channel }
10. ReplayPause                    { Channel }   ← 定格首帧（若 holdFirstFrame）
11. 状态 → CUED
12. 挂载 cutPoint 监听，同时下发 OBS 切场景指令
13. await cutPoint（事件）或 sleep(transitionTimeoutMs)（兜底）
14. ReplayPlay                     { Channel }   ← 遮罩退场时开始播放
15. 状态 → AIR
16. overlay.push({ mode:'replay', label: snapshot.playerName })
17. 释放锁
```

| ID | 需求 | 默认值 |
|---|---|---|
| B-REQ-501 | 前置校验全部通过才执行：`phase===ARMED`、vMix 连接、OBS 连接、`recording===true`、目标场景存在 | — |
| B-REQ-502 | `markDelayMs` 必须**可配置**，默认 = `loopLatencyMs` | 200ms |
| B-REQ-503 | 回放起点回溯量由 §5.6 的裁切参数统一驱动，**不得**另设一套独立参数 | — |
| B-REQ-504 | `holdFirstFrame` 可开关 | true |
| B-REQ-505 | `speed` 必须**可配置**，音游场景默认 1.0 | 1.0 |
| B-REQ-506 | 裁切后须记录实际耗时并写入日志（用于评估 `loopLatencyMs` 是否漂移） | — |
| B-REQ-507 | 步骤 13 必须由 cutPoint 信号或超时兜底**两者之一**驱动，任一先到即继续，**不得永久阻塞** | — |
| B-REQ-508 | 全流程失败时不得停留在瞬态，须迁移至 `FAULT` 或回退 `ARMED` | — |

> **B-REQ-509（打点补偿）**：由于回路延迟 L，vMix 缓冲区中「最新画面」落后操作员所见约 L。若不加 `markDelayMs`，**刚刚发生的精彩瞬间会被切掉在事件之外**。这是音游场景的高优先级缺陷，不可省略。

**首帧定格法（强烈建议开启）**

```
ReplayPlayLastEventToOutput → 立即 ReplayPause
```

因为画面静止：延迟多 100ms 少 100ms 都无所谓；转场期间无运动，不会有"动到一半被切"的违和感；不损失事件开头时间。

### 5.8 回程（回直播）

```
1. 前置校验：phase === AIR
2. OBS 切回 LIVE 场景（本地内容，不依赖回路）
3. overlay.push({ mode:'live', label: snapshot.playerName })
4. ReplayPause { Channel }     ★ 停在最后一帧，不用 ReplayLive
5. 状态 → RETURNING
6. sleep(200) → 状态 → ARMED
```

| ID | 需求 |
|---|---|
| B-REQ-601 | 回程**必须**先切 OBS、后动 vMix。理由：LIVE 是本地内容即时可用；反序会让观众看到通道切换瞬间 |
| B-REQ-602 | 回程**默认不得**调用 `ReplayLive`。理由：`ReplayLive` 使通道变为落后 L≈200ms 的直播直通，后续硬切会造成**画面倒退**（音游中比转场穿帮更明显） |
| B-REQ-603 | `ReplayLive` 仅作为独立的「手动找片段」功能，需二次确认 |
| B-REQ-604 | ⚠️ 须验证：通道处于回放态时 `recording` 是否仍为 `True`（R1）。若会导致录制中断，改回 `ReplayLive` 并接受倒退风险 |

### 5.14 转场防穿帮方案 ★

#### 5.14.1 问题定义

```
t=0      操作员按下按钮，OBS 开始 LIVE→REPLAY 转场
t=0~200  OBS 的 REPLAY 场景里，NDI 源显示的还是**切换前的内容**
         —— 也就是 vMix 输出的"直播直通"画面
t=200    回放画面才走完 vMix→NDI→OBS 的回路，真正到位
```

观众会看到：转场到 REPLAY，结果先看到直播画面，而且比刚才看的画面倒退了 ~200ms，然后才变成回放。**这就是穿帮。**

#### 5.14.2 核心原则

> **只允许一个"可见转场"，并且这个转场必须有一段"完全不透明的中段"，中段宽度 > 回路延迟。**

- **vMix 侧：所有切换一律硬切**（Cut，duration 0）。vMix 不做任何可见的转场
- **OBS 侧：唯一的可见转场**，把实际的场景切换动作藏在它遮住屏幕的那一刻

#### 5.14.3 Stinger + Transition Point

1. 做一个 600–800ms 的遮罩动画（WebM 带 alpha，首尾帧完全透明），中间有一段完全不透明区
2. Transition Point 设在"不透明区的正中间"
3. 程序同时发出 vMix 回放命令 **和** OBS 场景切换

**容差计算**：设不透明区为 200–600ms（宽 400ms），Transition Point = 400ms → 容差 **±200ms**。回路延迟约 200ms，够用。想要更宽松就做更长的遮罩——回放入场用 1 秒的全屏遮罩完全合理。

| ID | 需求 |
|---|---|
| B-REQ-1104 | REPLAY 场景须绑定 stinger 转场；LIVE 场景须设为 Cut |
| B-REQ-1105 | 转场时序须由 cutPoint 事件或超时兜底驱动，**不得**硬编码 `sleep(stingerDuration)` |
| B-REQ-1106 | 须提供降级方案：stinger 不可用时用 Fade + 足够长的时长（≥600ms）保证遮罩窗口 |

### 6.9 监看链路选型 ★

#### 6.9.1 方案对比

| 方案 | 端到端延迟 | 额外依赖 | 多设备 | 浏览器可用 | 评价 |
|---|---|---|---|---|---|
| **A. WHIP → MediaMTX → WHEP** | **200–500ms** | MediaMTX（单文件可执行） | ✅ | ✅ | **推荐主选** |
| **B. `GetSourceScreenshot` 轮询** | 1–3s（2–5fps） | **零额外依赖** | ✅ | ✅ | **零安装回退** |
| **C. RTMP → MediaMTX → HLS** | 3–10s | MediaMTX | ✅ | ✅ | 仅适合事后复核 |
| **D. OBS 虚拟摄像机** | ~0 | — | ❌ 单消费者 | ❌ | 不可用 |
| **E. NDI 直读** | 100–200ms | 需原生应用 | ✅ | ❌ 浏览器不支持 | 不可用于 Web 页 |
| **F. 采集卡回环** | 硬件级 | 硬件 | ❌ | — | 不推荐 |

**结论**：以 **A** 为主，**B** 为自动回退。

#### 6.9.2 ⚠️ WHIP 是推流，WHEP 是拉流

| 协议 | 全称 | 方向 | MediaMTX 端点 |
|---|---|---|---|
| **WHIP** | WebRTC HTTP **Ingest** Protocol | **推流（发布）** | `http://host:8889/live/whip` |
| **WHEP** | WebRTC HTTP **Egress** Protocol | **拉流（播放）** | `http://host:8889/live/whep` |

**正确链路**：

```
OBS ──WHIP 推流──► MediaMTX ──WHEP 拉流──► 解说 / 导播页浏览器
     :8889/live/whip          :8889/live/whep
```

**OBS 侧配置**（OBS 30.0 起内置 ✅）：

```
设置 → 直播 → 服务：WHIP
           服务器：http://<obs-host>:8889/live/whip
           承载令牌：（留空或按 MediaMTX 配置）
```

**浏览器播放**（已核验的两种嵌入方式）：

```html
<!-- 方式 1：iframe（最简单，但无法传凭据） -->
<iframe src="http://<mediamtx-ip>:8889/live?muted=true&autoplay=true&controls=false"></iframe>

<!-- 方式 2：reader.js + <video>（推荐，可控性强） -->
<video id="mon" muted autoplay playsinline></video>
<script src="./reader.js"></script>
<script>
  new MediaMTXWebRTCReader({
    url: "http://<mediamtx-ip>:8889/live/whep",
    onError: (e) => console.error(e),
    onTrack: (e) => document.getElementById('mon').srcObject = e.streams[0],
  });
</script>
```

| ID | 需求 |
|---|---|
| C-REQ-401 | 主用 `reader.js` + `<video>` 方式；iframe 仅作为快速验证手段 |
| C-REQ-402 | 若启用 MediaMTX 认证，**必须**使用 `reader.js` 方式 ✅（iframe 无法传凭据） |

#### 6.9.3 ★ 多路输出架构决策（RC5）

**关键事实**：OBS 的各输出通道能力如下 ——

| 输出类型 | 可并行数量 | 说明 |
|---|---|---|
| **直播（Stream）** | **1 个** | ⚠️ **WHIP 属于这一路**，与 RTMP 到平台**默认互斥** |
| 录制 | 1 个 | 与直播并行 ✅ |
| **NDI Dedicated Output（滤镜）** | **多个** ✅ | 挂任意源/场景，独立于直播输出 |
| 虚拟摄像机 | 1 个 | 单消费者，浏览器不可用 |
| `obs-multi-rtmp` 插件 | **多个 RTMP** ✅ | 社区插件（sorayuki/obs-multi-rtmp） |

> ✅ 好消息：**NDI 那一路完全独立**，CLEAN → vMix 链路不受推流架构影响。

**三种解法（按推荐度）**：

**方案 ①（推荐）：obs-multi-rtmp 双路 RTMP，路径隔离**

```
OBS ──RTMP #1──► 直播平台（B站/YouTube）
    └─RTMP #2──► MediaMTX ──WHEP──► 解说页
```
- ✅ **故障隔离**：MediaMTX 挂了不影响主推流
- ✅ 解说延迟 ≈ 1–2s（对"提示"足够，对"看画面"偏慢）
- ⚠️ 需装社区插件

**方案 ②：OBS → WHIP → MediaMTX → 转发 RTMP 给平台**

```
OBS ──WHIP──► MediaMTX ──┬──WHEP──► 解说页（200–500ms ★ 最低延迟）
                         └──RTMP forward──► 直播平台
```
- ✅ **延迟最低**；MediaMTX 官方支持 forward ✅
- ⚠️ **MediaMTX 成为单点**：它挂了主推流也断
- ⚠️ 平台侧收到的是转发流，排查链条变长

**方案 ③：MediaMTX 从平台回拉**
- 最省事但延迟最高（3–10s），**不适合解说场景**

| ID | 需求 |
|---|---|
| C-REQ-410 | 架构决策须在开发前完成（RC5）。建议：解说需实时看画面 → 方案 ②；仅收文字提示 → 方案 ① |
| C-REQ-411 | 若采用方案 ②，须为 MediaMTX 增加看门狗与健康检查 |

## 10. 里程碑与推进顺序

### 10.1 全局推进顺序（按价值/风险排序）

| 优先级 | 阶段 | 理由 |
|---|---|---|
| **1** | **B-R0 物理链路验证** | 回放链路是否成立的前提；不通则整个 B 重新设计 |

| **3** | **C-MC1/MC2 提示 + 倒计时** | **完全不依赖任何视频链路**，今天就能开始做，解说马上受益 ★ 投入产出比最高 |

| **5** | B 转场联动 → C 编排对接 | 两者合流才是完整的一键回放 |
| **6** | 模块 A | 相对独立，可并行 |

| # | 项 | 验证方法 | 影响 |

| **R2** | NDI 源能否直接加入 vMix 回放机位 | 手动添加并录制播放，看是否黑屏 | 若黑屏，改用「NDI 输入 → Output 2/3 → 该 Output 作回放源」变通 |
